# "Buy the dev a coffee" — IAP tip jar setup & bring-up

The iOS support flow is a **native StoreKit consumable tip jar** (`expo-iap`). This is the
bench/bring-up guide: the manual App Store Connect work, local testing, and what to do if a
purchase won't go through. Android is unaffected (it keeps the external Ko-fi link in
`src/lib/support.ts`).

> **Why IAP, not the old external link:** Apple guideline **3.1.1** explicitly permits *"in-app
> purchase … to 'tip' the developer."* An external payment link is a review-rejection risk outside
> the US storefront. Wording is **"tip"/"coffee"/"support"**, never **"donation"** (3.2.2 reserves
> charitable donations for approved nonprofits). The tip **unlocks nothing**, so StoreKit 2 verifies
> on-device and **no server/receipt backend** is needed.

## Products (consumables)

Three **consumable** products — repurchasable, never restored, grant nothing. **Product IDs must
match `TIP_SKUS` in `src/lib/iap.ts` exactly.**

| Tier | UI label | Price (USD anchor) | Product ID |
|------|----------|--------------------|------------|
| Small | A coffee | $1.99 | `com.zanderhalverson.hale.tip.small` |
| Medium | A few coffees | $4.99 | `com.zanderhalverson.hale.tip.medium` |
| Large | A week of coffee | $9.99 | `com.zanderhalverson.hale.tip.large` |

Prices are read **live from the store** (`product.displayPrice`, localized per storefront) — the
USD figures above only live in App Store Connect + `Hale.storekit`, never hard-coded in the app.

## One-time App Store Connect setup (required — do this before submitting)

1. **Paid Apps Agreement.** App Store Connect → **Business** → sign the Paid Applications Agreement;
   it must be **Active**. Complete **banking** + **tax** info and set a **tax category** per product.
   Required even to test in the sandbox. *(A free/personal Apple team cannot do this — the tip UI
   degrades to an "unavailable" state on personal-team builds, which is expected.)*
2. **Create three Consumable IAPs.** App Store Connect → app **6776380902** → **Monetization →
   In-App Purchases → +** → Type **Consumable**. For each: Reference Name (e.g. "Tip - A coffee"),
   the exact **Product ID** from the table, a price, ≥1 localization (Display Name + Description), and
   a review screenshot + notes.
3. **Submit the first IAP _with_ the next app version.** Hale is already live, so the first-ever IAP
   **cannot** be approved on its own — attach all three to the next binary submission
   (`eas build` + `eas submit`). Later IAPs can ship without a new binary.
4. **Sandbox testers.** Users and Access → **Sandbox → +**; use an email **never** used as an Apple
   Account. On-device, sign in under **Settings → Developer → Sandbox Apple Account**. TestFlight
   builds run against sandbox automatically. Use **Clear Purchase History** to re-test. Metadata can
   take ~1 hour to appear.

## No entitlement, no server

- **No "In-App Purchase" entitlement to add.** IAP works for any app with an explicit (non-wildcard)
  App ID — `com.zanderhalverson.hale` qualifies. Nothing to add to `ios.entitlements`, and (unlike
  the push entitlement) nothing to strip for personal-team builds.
- **No receipt server.** A consumable tip unlocks nothing; StoreKit 2 verifies the transaction
  on-device. The only mandatory step is `finishTransaction({ purchase, isConsumable: true })` (done in
  `useTipJar`'s `onPurchaseSuccess`) — skip it and the purchase replays on every launch and can't be
  tipped again.

## Local testing (no App Store Connect round-trip)

`storekit/Hale.storekit` mirrors the three consumables. Because `ios/` is regenerated by prebuild,
point the run scheme at it manually:

1. `npx expo prebuild -p ios` (autolinks the `expo-iap` pod — confirm it lands in `ios/Podfile.lock`).
2. Open `ios/Hale.xcworkspace` → **Product → Scheme → Edit Scheme → Run → Options → StoreKit
   Configuration** → select `Hale.storekit`.
3. `npx expo run:ios --device` (or simulator — StoreKit testing works in the simulator, unlike most
   native features). Tips complete instantly against the local config; no sandbox account needed.

Needs a **dev/prod build** (no Expo Go — `tipJarSupported` is false there, so the screen falls back to
the Ko-fi link). `eas build` runs prebuild, so the pod + plugin ship automatically.

## If a tip won't go through

| Symptom | Likely cause / fix |
|---------|-------------------|
| Tip screen shows "the coffee shop is closed" (`UnavailableBody`) | `products` came back empty: Paid Apps Agreement not Active, products not yet **Approved**/"Ready to Submit", Product IDs don't match `TIP_SKUS`, or you're on a personal team. |
| Spinner never resolves | A pending (Ask-to-Buy / SCA) transaction — it resolves later via the listener. Otherwise check the device is signed into a **sandbox** account, not production iCloud. |
| Purchase repeats on every launch | `finishTransaction` not being called — verify `onPurchaseSuccess` runs and uses `isConsumable: true`. |
| `expo-doctor` flags `expo-iap` as "Unmaintained" | Known false positive (stale RN-Directory metadata, expo/expo#44980). The package is actively maintained in the OpenIAP monorepo. Safe to ignore. |
| Prices show as "$0.00" / wrong currency | Reading a hard-coded value instead of `product.displayPrice`. The app reads `displayPrice` — check the product loaded. |

## Library note

`expo-iap@^4.3.1` (StoreKit 2 on iOS, Play Billing on Android — Android unused here). Pinned
explicitly because its peerDeps are wildcards. `requestPurchase` uses `{ request: { apple, google },
type: 'in-app' }` in 4.3.x — re-verify the request-key shape against the installed TS types on any
major bump, since it has churned across versions.
